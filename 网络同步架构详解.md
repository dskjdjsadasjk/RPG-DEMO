## 1. 总体架构概览

本系统是一套**自研的、UE 风格的、面向 Dedicated Server 架构的 Unity 网络同步框架**。它不是 Mirror / Netcode for GameObjects / Photon 的封装，而是从传输层到应用层完全自建，借鉴了 Unreal Engine 的 `UNetDriver` / `UNetConnection` / `UActorChannel` / `AGameModeBase` 等概念。

### 核心设计决策

| 决策 | 选择 | 原因 |
|---|---|---|
| 网络拓扑 | Dedicated Server（权威服务器） | 所有游戏状态以服务端为唯一权威，杜绝客户端作弊 |
| 传输层 | Unity Transport Package (UTP) | 官方维护、跨平台、支持 Reliable Sequenced Pipeline |
| 架构抽象 | 自定义 `INetworkTransport` 接口 | 上层逻辑不直接依赖 UTP，可替换为 WebSocket / Steamworks 等 |
| 序列化 | 手写小端二进制 Reader/Writer | 零反射、零 GC 分配（读取时）、固定包大小，性能可控 |
| 复制模型 | Actor Channel + ObjectReplicator（逐组件） | 每个连接对每个 Actor 有独立 Channel，组件级增量复制 |
| 移动同步 | 客户端预测 + 服务端纠错 + 快照插值 | 本地零延迟操作体验 + 远程平滑显示 |
| Tick 模型 | 固定 TickRate（默认 60Hz）时钟 | 服务端权威推进，客户端通过 ServerWelcome 对齐时钟 |

### 数据流总览

```
┌──────────────┐     byte[] packet      ┌──────────────┐
│  Client App  │ ◄──────────────────►   │  Server App  │
│              │   UDP / UTP Transport   │              │
│ GameNetDriver│                         │ GameNetDriver│
│  ├ Connection│                         │  ├ Connection│
│  ├ ActorChan │                         │  ├ ActorChan │
│  └ Replicator│                         │  └ Replicator│
└──────────────┘                         └──────────────┘
```

## 2. 分层设计与模块职责

```
Networking/
├── Transport/          传输抽象层 — 隔离底层 UDP/UTP
├── Protocol/           协议序列化层 — 定义所有网络消息的编解码
├── Identity/           身份与注册 — NetId 分配、Prefab 映射、对象注册表
├── Replication/        复制系统 — ActorChannel、组件级状态复制、移动同步
├── Bootstrap/          引导 — 根据启动参数创建 DS 或 Client
├── Server/             服务端逻辑 — GameMode 登录、Pawn 生成
├── Client/             客户端逻辑 — 本地 PlayerController Possess
├── Diagnostics/        诊断 — OnGUI 调试 HUD
├── GameNetDriver.cs    核心网络驱动 — 连接管理、握手、分发、Tick 循环

         │
    GameNetDriver / GameNetConnection       (核心驱动)
         │

         │
    Identity (NetworkIdentity / Registry)
         │
    Protocol (Connection / Actor / ObjectReplication / CharacterMovement)
         │
    Transport (INetworkTransport / UtpTransport)
```

## 3. 传输层 Transport

### 3.1 `TransportTypes.cs`

**作用**：定义传输层的公共类型，不依赖任何具体传输实现。

#### `TransportConnectionHandle`（readonly struct）

```csharp
public readonly struct TransportConnectionHandle : IEquatable<TransportConnectionHandle>
```

- **为什么这么设计**：连接句柄是一个**值类型整数包装器**，避免在各处传递引用类型的连接对象。值类型无 GC 压力，可直接作为 Dictionary 的 Key。
- `Value`：内部整数 ID，`> 0` 表示有效。
- `IsValid`：`Value > 0` 时为 `true`。
- `Invalid`：静态空句柄（值为 0），用于表示"无连接"。
- 实现了 `IEquatable<TransportConnectionHandle>` 和 `GetHashCode`，使其可作为字典键。

#### `TransportEventType`（enum）

```csharp
public enum TransportEventType : byte
{
    Connected,    // 新连接建立
    Data,         // 收到数据包
    Disconnected  // 连接断开
}
```

#### `TransportDelivery`（enum）

```csharp
public enum TransportDelivery : byte
{
    Unreliable,  // 不保证到达、不保证顺序（用于高频移动快照）
    Reliable     // 保证到达、保证顺序（用于握手、Spawn、初始状态）
}
```

**为什么区分两种投递模式**：
- **Reliable**：握手、ActorChannel Open/Close、初始状态 — 这些消息**丢了就会出严重问题**（比如对象没生成），必须可靠。
- **Unreliable**：每帧移动快照、MoveAck — 这些消息**频率高、最新值覆盖旧值**，丢了旧的无所谓，用 Reliable 反而造成延迟堆积。

#### `TransportEvent`（readonly struct）

```csharp
public readonly struct TransportEvent
{
    public TransportEventType Type { get; }
    public TransportConnectionHandle Connection { get; }
    public byte[] Payload { get; }    // 仅 Data 事件有值
    public string Reason { get; }     // 仅 Disconnected 事件有值
}
```

- **为什么用事件队列而非回调**：`PollEvents(List<TransportEvent>)` 让调用方（`GameNetDriver`）在**自己的 Tick 中集中处理**所有事件，而非在传输层线程中回调，避免了线程安全和执行顺序问题。

### 3.2 `INetworkTransport.cs`

**作用**：传输层抽象接口，定义所有传输实现必须满足的契约。

```csharp
public interface INetworkTransport : IDisposable
{
    bool IsCreated { get; }
    bool IsServer { get; }
    ushort BoundPort { get; }

    void StartServer(ushort port);
    TransportConnectionHandle StartClient(string address, ushort port);
    void PollEvents(List<TransportEvent> output);
    bool Send(TransportConnectionHandle connection, ArraySegment<byte> payload, TransportDelivery delivery);
    void Flush();
    void Disconnect(TransportConnectionHandle connection);
    string GetRemoteEndpoint(TransportConnectionHandle connection);
}
```

**函数职责**：

| 函数 | 作用 |
|---|---|
| `StartServer` | 在指定 UDP 端口开始监听，进入服务器模式 |
| `StartClient` | 向目标地址发起连接，返回连接句柄 |
| `PollEvents` | 拉取自上次以来的所有网络事件（连接/数据/断开），填入 output 列表 |
| `Send` | 向指定连接发送数据，选择可靠或不可靠投递 |
| `Flush` | 将所有已 Send 的数据真正刷出到网络（UTP 是批量发送模式） |
| `Disconnect` | 主动断开指定连接 |
| `GetRemoteEndpoint` | 获取对端地址字符串（用于日志） |

**为什么用接口而非直接用 UTP**：解耦。未来可以替换为 WebSocket、Steam P2P、Epic Online Services 等传输层，上层 `GameNetDriver` 无需改动。

### 3.3 `UtpTransport.cs`

**作用**：基于 Unity Transport Package (UTP) 的传输层实现，是 `INetworkTransport` 的默认实现。

#### 关键字段

```csharp
private NetworkDriver driver;
private NetworkPipeline reliablePipeline;
private readonly Dictionary<int, NetworkConnection> connections;
```

- `driver`：UTP 的核心 `NetworkDriver`，管理所有底层 socket 操作。
- `reliablePipeline`：UTP 的 `ReliableSequencedPipelineStage` 管线，保证消息可靠有序到达。
- `connections`：内部 `int → NetworkConnection` 映射，将自定义的 `TransportConnectionHandle` 与 UTP 的 `NetworkConnection` 关联。

#### `StartServer(ushort port)`

```csharp
driver = NetworkDriver.Create();
reliablePipeline = driver.CreatePipeline(typeof(ReliableSequencedPipelineStage));
NetworkEndpoint endpoint = NetworkEndpoint.AnyIpv4.WithPort(port);
driver.Bind(endpoint);
driver.Listen();
```

- 创建 UTP Driver，建立 Reliable 管线。
- 绑定到 `0.0.0.0:port`，开始监听。
- 如果 Bind 或 Listen 失败则抛异常并 Dispose。

#### `StartClient(string address, ushort port)`

- 解析地址为 `NetworkEndpoint`（支持 IPv4/IPv6，不支持 DNS）。
- 创建 Driver 和 Reliable 管线。
- 调用 `driver.Connect(endpoint)` 发起连接。
- 将 `NetworkConnection` 注册到内部映射，返回 `TransportConnectionHandle`。

#### `PollEvents(List<TransportEvent> output)`

这是最核心的方法，负责将 UTP 的底层事件转换为统一的 `TransportEvent`：

1. `driver.ScheduleUpdate().Complete()` — 推进 UTP 内部状态机（同步等待完成）。
2. **服务器模式**：循环 `driver.Accept()` 接受所有新连接，生成 `Connected` 事件。
3. 遍历所有已知连接，循环 `connection.PopEvent(driver, out reader)`：
   - `NetworkEvent.Type.Connect` — 客户端模式下生成 `Connected` 事件。
   - `NetworkEvent.Type.Data` — 将 UTP 的 `DataStreamReader` 逐字节拷贝到 `byte[]`，生成 `Data` 事件。
   - `NetworkEvent.Type.Disconnect` — 读取 UTP 断连原因，生成 `Disconnected` 事件，标记连接待移除。
4. 清理已断开的连接。

**为什么逐字节读取而非 `reader.ReadBytes`**：UTP 的 `DataStreamReader` API 在该版本下只提供 `ReadByte`，没有批量读取安全 API，所以用循环拷贝。

#### `Send(TransportConnectionHandle, ArraySegment<byte>, TransportDelivery)`

```csharp
NetworkPipeline pipeline = delivery == TransportDelivery.Reliable
    ? reliablePipeline
    : NetworkPipeline.Null;
driver.BeginSend(pipeline, utpConnection, out DataStreamWriter writer, payload.Count);
// 逐字节写入
driver.EndSend(writer);
```

- Reliable 消息走 `reliablePipeline`（保证到达+顺序）。
- Unreliable 消息走 `NetworkPipeline.Null`（裸 UDP）。

#### `Flush()`

```csharp
driver.ScheduleFlushSend().Complete();
```

UTP 的发送是**延迟批量**的：`Send` 只是把数据写入内部缓冲区，真正发到网络需要调用 `ScheduleFlushSend`。`GameNetDriver.Tick` 结束时统一 Flush。

## 4. 协议层 Protocol

协议层定义了所有网络消息的**二进制编解码**。所有消息的第一个字节是**消息类型标识**（MessageType），用于分发。

### 4.1 `NetworkPacketCodec.cs`

**作用**：底层的二进制读写器，所有协议消息的序列化基础。

#### `NetworkPacketWriter`（internal sealed class）

```csharp
internal sealed class NetworkPacketWriter
{
    private readonly byte[] buffer;
    private int position;
}
```

- **为什么用预分配 `byte[]` 而非 `MemoryStream`**：每个协议消息在 `Create*` 时传入精确 capacity，`ToArray()` 时如果 `position == buffer.Length` 则直接返回原数组，**零额外分配**。
- 写入方法：`WriteByte`、`WriteUInt16`、`WriteUInt32`、`WriteUInt64`、`WriteSingle`（float）、`WriteBytes`。
- 全部使用**小端序**（Little-Endian）：`buffer[position++] = (byte)(value >> shift)`。

#### `NetworkPacketReader`（internal sealed class）

```csharp
internal sealed class NetworkPacketReader
{
    private readonly byte[] buffer;
    private int position;
}
```

- 所有 `TryRead*` 方法返回 `bool`，失败时（缓冲区不足）返回 `false` 而非抛异常。这使得协议解析可以链式短路：

```csharp
return reader.TryReadExpectedByte(...)
    && reader.TryReadUInt16(out ...)
    && reader.IsAtEnd;
```

- `IsAtEnd`：`position == buffer.Length`，用于校验包是否**恰好读完**（防止多余/缺失字节）。
- `TryReadString`：先读 1 字节长度，再读 UTF-8 字节，有最大长度保护。
- `TryReadBytes`：读取指定长度的字节块。

#### `FloatUInt32`（internal struct）

```csharp
[StructLayout(LayoutKind.Explicit)]
internal struct FloatUInt32
{
    [FieldOffset(0)] public float Float;
    [FieldOffset(0)] public uint UInt32;
}
```

- **为什么用 `LayoutKind.Explicit`**：这是 C# 的 **type punning**（类型双关）技巧，通过 union 重解释 float 和 uint 的内存，实现**零拷贝浮点序列化**，比 `BitConverter.SingleToInt32Bits` 兼容性更好（旧 .NET 版本没有后者）。

### 4.2 `ConnectionProtocol.cs`

**作用**：定义连接握手阶段的所有消息。

#### 消息类型枚举

```csharp
public enum ConnectionMessageType : byte
{
    ClientHello = 1,      // 客户端发起握手
    ServerChallenge = 2,  // 服务端回挑战
    ClientLogin = 3,      // 客户端登录
    ServerWelcome = 4,    // 服务端欢迎（分配 ConnectionId）
    ClientReady = 5,      // 客户端就绪
    ServerReject = 6      // 服务端拒绝
}
```

#### 拒绝原因枚举

```csharp
public enum ConnectionRejectReason : byte
{
    InvalidPacket, ProtocolMismatch, SchemaMismatch,
    InvalidChallenge, InvalidLogin, UnexpectedMessage, HandshakeTimeout
}
```

#### 常量

```csharp
public const ushort ProtocolVersion = 1;     // 协议版本号
public const uint SchemaHash = 0x52504734;   // "RPG4" 的 ASCII，用于校验协议一致性
public const int MaxDisplayNameBytes = 32;   // 显示名最大字节
```

**为什么需要 SchemaHash**：当协议消息结构变更（增删字段）后，旧客户端连新服务器会因为字段错位而崩溃。SchemaHash 是一个**编译期常量**，客户端和服务端必须一致才能握手成功，类似于 API 版本校验。

#### 各消息的编解码函数

| 函数 | 消息 | 字段布局 |
|---|---|---|
| `CreateClientHello` / `TryReadClientHello` | ClientHello | Type:u8, ProtocolVersion:u16, SchemaHash:u32, ClientNonce:u64 |
| `CreateServerChallenge` / `TryReadServerChallenge` | ServerChallenge | Type:u8, ProtocolVersion:u16, ClientNonce:u64, ServerNonce:u64 |
| `CreateClientLogin` / `TryReadClientLogin` | ClientLogin | Type:u8, ServerNonce:u64, NameLength:u8, Name:UTF8 |
| `CreateServerWelcome` / `TryReadServerWelcome` | ServerWelcome | Type:u8, ConnectionId:u32, ServerTick:u32, TickRate:u16 |
| `CreateClientReady` / `TryReadClientReady` | ClientReady | Type:u8, ConnectionId:u32 |
| `CreateServerReject` / `TryReadServerReject` | ServerReject | Type:u8, Reason:u8, MsgLen:u8, Message:UTF8 |

#### `TryReadMessageType`

```csharp
public static bool TryReadMessageType(byte[] packet, out ConnectionMessageType messageType)
{
    messageType = (ConnectionMessageType)packet[0];
    return Enum.IsDefined(typeof(ConnectionMessageType), messageType);
}
```

- 读取首字节，检查是否是合法的枚举值。`GameNetDriver.HandlePacket` 用此方法做消息分发。

**Nonce 机制的作用**：`ClientNonce` 和 `ServerNonce` 是随机生成的 64 位数，用于防止握手消息重放攻击和确认握手双向活体。ClientHello 带 ClientNonce，ServerChallenge 回显它并加 ServerNonce，ClientLogin 回带 ServerNonce — 形成三方握手确认。

### 4.3 `ActorProtocol.cs`

**作用**：定义网络对象生命周期（Spawn / Despawn）的消息。

#### 消息类型

```csharp
public enum ActorMessageType : byte
{
    ActorChannelOpen = 16,      // 服务端→客户端：生成对象
    ActorChannelOpenAck = 17,   // 客户端→服务端：确认生成
    ActorChannelClose = 18      // 服务端→客户端：销毁对象
}
```

**为什么从 16 开始编号**：与 Connection 消息（1-6）区分，避免首字节歧义。各协议的消息类型空间不重叠（Connection: 1-6, Actor: 16-18, ObjectReplication: 32, CharacterMovement: 48-50）。

#### `ActorSpawnMessage`（readonly struct）

包含 `ChannelId`、`NetId`、`PrefabId`、`OwnerConnectionId`、`AuthorityEpoch`、`Position`、`Rotation`。

#### `ActorChannelCloseReason`

```csharp
public enum ActorChannelCloseReason : byte
{
    Destroyed = 1,           // 对象被显式销毁
    OwnerDisconnected = 2,   // 拥有者断线
    ServerShutdown = 3,      // 服务器关闭
    ProtocolError = 4        // 协议错误
}
```

#### `CreateActorChannelOpen` / `TryReadActorChannelOpen`

布局：`Type:u8, ChannelId:u16, NetId:u32, PrefabId:u16, OwnerConnectionId:u32, AuthorityEpoch:u16, Position:(3×f32), Rotation:(4×f32)` = 43 字节。

读取时做严格校验：
- `channelId`、`netId`、`prefabId`、`authorityEpoch` 不能为 0。
- 位置和旋转的每个分量必须 `IsFinite`（非 NaN、非 Infinity）。
- 旋转不能是全零四元数。
- 四元数会被 `normalized` 归一化。

#### `AuthorityEpoch` 的作用

每次对象被重新 Spawn（例如断线重连后）`AuthorityEpoch` 会递增。消息中携带 Epoch 可以**防止旧连接的残留包误操作新对象** — 如果收到包的 Epoch 与当前对象不匹配，直接拒绝。

### 4.4 `ObjectReplicationProtocol.cs`

**作用**：定义组件级状态复制的消息。

```csharp
public enum ObjectReplicationMessageType : byte
{
    ObjectState = 32
}

[Flags]
public enum ObjectStateFlags : byte
{
    None = 0,
    Initial = 1   // 初始状态（首次同步）
}
```

#### `ObjectStateMessage`（readonly struct）

包含 `ChannelId`、`NetId`、`AuthorityEpoch`、`ReplicationId`（组件 ID）、`Sequence`（序列号）、`Flags`、`State`（原始字节）。

#### `CreateObjectState` / `TryReadObjectState`

布局：`Type:u8, ChannelId:u16, NetId:u32, AuthorityEpoch:u16, ReplicationId:u16, Sequence:u16, Flags:u8, StateLength:u16, State:bytes`。

- `Flags` 只允许 `None` 或 `Initial`，未知标志位会被拒绝。

### 4.5 `CharacterMovementProtocol.cs`

**作用**：定义角色移动同步的三个消息。

```csharp
public enum CharacterMovementMessageType : byte
{
    ClientMove = 48,          // 客户端→服务端：本帧移动输入
    ServerMoveAck = 49,       // 服务端→客户端：移动确认+权威状态
    TransformSnapshot = 50    // 服务端→客户端：模拟代理的位置快照
}
```

#### `CharacterMoveMessage`

客户端发送的移动输入包：

| 字段 | 类型 | 说明 |
|---|---|---|
| NetId | u32 | 目标角色 |
| AuthorityEpoch | u16 | 防 Epoch 漂移 |
| Sequence | u32 | 移动序列号（递增） |
| ClientTick | u32 | 客户端本地 Tick |
| DeltaTime | f32 | 本帧时间增量 |
| WorldInput | 3×f32 | 世界空间输入向量（归一化） |
| ControlYaw | f32 | 控制旋转 Yaw 角 |

固定 35 字节。读取时校验 `deltaTime > 0`、输入向量模长 `≤ 1.0001`、所有浮点 `IsFinite`。

#### `CharacterMoveAckMessage`

服务端对客户端移动的确认，携带**权威位置/速度**：

| 字段 | 类型 | 说明 |
|---|---|---|
| NetId | u32 | |
| AuthorityEpoch | u16 | |
| AcknowledgedSequence | u32 | 确认到的移动序列号 |
| ServerTick | u32 | 服务端当前 Tick（客户端用于时钟对齐） |
| Position | 3×f32 | 权威位置 |
| Rotation | 4×f32 | 权威旋转 |
| Velocity | 3×f32 | 权威速度 |
| MovementMode | u8 | 移动模式枚举 |

固定 56 字节。

#### `CharacterSnapshotMessage`

服务端发给**模拟代理**（其他玩家）的位置快照：

| 字段 | 类型 | 说明 |
|---|---|---|
| NetId | u32 | |
| AuthorityEpoch | u16 | |
| ServerTick | u32 | 快照对应的服务端 Tick |
| Position / Rotation / Velocity | 同上 | |
| MovementMode | u8 | |

固定 52 字节。

**为什么 MoveAck 和 Snapshot 分开**：
- `MoveAck` 只发给**拥有者**（AutonomousProxy），包含 `AcknowledgedSequence`，用于预测纠错。
- `TransformSnapshot` 发给**非拥有者**（SimulatedProxy），用于插值显示，不需要 Sequence。

#### `AllocateNetId`

```csharp
private uint AllocateNetId()
{
    uint firstCandidate = nextNetId;
    do {
        uint candidate = nextNetId++;
        if (nextNetId == 0) nextNetId = 1;  // 跳过 0（保留值）
        if (candidate != 0 && !objects.ContainsKey(candidate))
            return candidate;
    } while (nextNetId != firstCandidate);
    throw new InvalidOperationException("Network NetId space is exhausted.");
}
```

- 循环递增，跳过 0，跳过已占用的 ID。
- 如果绕一圈回到起点说明 ID 空间耗尽（uint 42 亿个，实际不会发生）。

#### `Unregister` / `Clear`

- `Unregister`：从字典移除，调用 `ResetNetworkSpawn`，可选销毁 GameObject。
- `Clear`：清空所有对象（断线/停机时调用），重置 `nextNetId = 1`。

#### 关键设计

- `OnNetworkSpawned` / `OnNetworkDespawned` / `OnReplicatedStateApplied`：子类可选的生命周期回调。

#### `CaptureReplicatedState` / `TryApplyReplicatedState`（internal）

```csharp
internal byte[] CaptureReplicatedState()
{
    ReplicationStateWriter writer = new ReplicationStateWriter();
    WriteReplicatedState(writer);
    return writer.ToArray();
}

internal bool TryApplyReplicatedState(byte[] state, bool isInitialState)
{
    ReplicationStateReader reader = new ReplicationStateReader(state);
    if (!ReadReplicatedState(reader) || !reader.IsAtEnd)
        return false;
    OnReplicatedStateApplied(isInitialState);
    return true;
}
```

- `CaptureReplicatedState`：服务端调用，将当前状态序列化为 `byte[]`。
- `TryApplyReplicatedState`：客户端调用，将收到的状态反序列化并应用。
- `!reader.IsAtEnd` 校验：确保读完了所有字节，防止序列化不一致。

### 6.3 `ObjectReplicator.cs`

**作用**：包装一个 `NetworkBehaviour`，管理其状态的增量检测、序列号和应用。

```csharp
public sealed class ObjectReplicator
{
    private byte[] lastSentState;       // 上次发送的状态（用于增量检测）
    private ushort nextSequence = 1;    // 下一个序列号
    private ushort lastAppliedSequence; // 上次应用的序列号（客户端）
    private bool hasAppliedSequence;    // 是否已应用过任何序列
}
```

#### `TryCaptureState(bool force, out ushort sequence, out byte[] state)`

服务端调用：
1. 调用 `Target.CaptureReplicatedState()` 获取当前状态字节。
2. 如果 `!force` 且状态与 `lastSentState` 相同（`StatesEqual`），返回 `false`（跳过发送）。
3. 否则分配序列号，更新 `lastSentState`，返回 `true`。

**为什么有增量检测**：避免每帧发送相同的状态（如血量没变就不发），节省带宽。

**为什么有 `force` 参数**：首次发送（Initial State）必须强制发送，即使状态看起来是默认值。

#### `TryApplyState(ushort sequence, byte[] state, bool isInitialState, out bool applied)`

客户端调用：
1. 如果 `sequence` 不比 `lastAppliedSequence` 新（`IsNewerSequence`），跳过但返回 `true`（旧包不算错误）。
2. 调用 `Target.TryApplyReplicatedState(state, isInitialState)`。
3. 更新 `lastAppliedSequence`。

#### `IsNewerSequence`（静态方法）

```csharp
private static bool IsNewerSequence(ushort candidate, ushort current)
{
    ushort delta = (ushort)(candidate - current);
    return delta != 0 && delta < 0x8000;
}
```

- **环形序列号比较**：`ushort` 会回绕（65535 → 0），用"差值 < 半圈"判断是否更新。
- 这是网络编程中处理序列号回绕的标准技巧。

    float deltaTime = Mathf.Clamp(Time.deltaTime, 1f / 240f, MaxMoveDeltaTime);

**为什么保存 `PredictedPosition`**：收到服务端 Ack 时，对比预测位置和权威位置，判断是否需要纠错。

#### 拥有者纠错：`ReceiveServerMoveAck`

```csharp
public void ReceiveServerMoveAck(CharacterMoveAckMessage ack)
{
    // 1. 校验：必须是 AutonomousProxy，序列号必须更新
    lastAckedMoveSequence = ack.AcknowledgedSequence;

    // 2. 找到对应的 SavedMove，计算位置误差
    int acknowledgedIndex = FindSavedMoveIndex(ack.AcknowledgedSequence);
    float positionError = acknowledgedIndex >= 0
        ? Vector3.Distance(savedMoves[acknowledgedIndex].PredictedPosition, ack.Position)
        : Vector3.Distance(transform.position, ack.Position);

    // 3. 移除已确认的移动
    RemoveAcknowledgedMoves(ack.AcknowledgedSequence);

    // 4. 如果误差超过阈值，回滚重放
    if (positionError <= OwnerCorrectionDistance) return;

    movement.ApplyNetworkState(ack.Position, ack.Rotation, ack.Velocity, ack.MovementMode);

    // 5. 重放所有未确认的移动
    for (int i = 0; i < savedMoves.Count; i++)
    {
        movement.SimulateNetworkMove(savedMoves[i].WorldInput, savedMoves[i].DeltaTime);
        savedMoves[i].PredictedPosition = transform.position;
        savedMoves[i].PredictedRotation = transform.rotation;
        savedMoves[i].PredictedVelocity = movement.Velocity;
    }
    correctionCount++;
}
```

**预测纠错的完整逻辑**：
1. 收到服务端对某个 `Sequence` 的确认。
2. 对比**当时预测的位置**与**服务端权威位置**。
3. 如果误差小（<5cm），直接丢弃已确认的移动，无需纠错。
4. 如果误差大，将角色**回退到服务端权威位置**，然后**重新模拟**所有未确认的移动（Replay），更新预测结果。

**为什么阈值是 5cm**：太小会导致频繁纠错（抖动），太大会让作弊者有机可乘。5cm 是一个经验平衡值。

#### 服务端处理：`TryProcessServerMove`

```csharp
public bool TryProcessServerMove(CharacterMoveMessage move, out string validationError)
{
    // 1. 校验：必须是 Authority，DeltaTime 在合理范围，输入模长 ≤ 1
    if (move.DeltaTime <= 0f || move.DeltaTime > MaxMoveDeltaTime) ...;
    if (move.WorldInput.sqrMagnitude > 1.0001f) ...;

    // 2. 丢弃旧序列
    if (!IsNewerSequence(move.Sequence, lastServerMoveSequence)) return true;

    // 3. 设置控制旋转
    character.Controller.SetControlRotation(Quaternion.Euler(0f, move.ControlYaw, 0f));

    // 4. 模拟移动（权威执行）
    movement.SimulateNetworkMove(move.WorldInput, move.DeltaTime);
    lastServerMoveSequence = move.Sequence;
    return true;
}
```

**服务端校验逻辑**：
- `DeltaTime` 限制在 `(0, 0.1]`：防止客户端发送超大 dt 穿墙。
- 输入模长限制：防止加速作弊。
- 序列号去重：防止旧包重放。

#### 模拟代理插值：`ReceiveSnapshot` + `InterpolateSimulatedProxy`

```csharp
public void ReceiveSnapshot(CharacterSnapshotMessage snapshot)
{
    // 校验 + 添加到缓冲区
    snapshots.Add(snapshot);
    if (snapshots.Count > MaxSnapshots) snapshots.RemoveAt(0);
    if (snapshots.Count == 1) ApplySnapshot(snapshot); // 首个直接应用
}

private void InterpolateSimulatedProxy()
{
    // 1. 计算渲染 Tick = 当前服务端 Tick - 延迟
    double renderTick = estimatedServerTick - InterpolationDelayTicks;

    // 2. 丢弃过旧的快照（snapshots[1].ServerTick <= renderTick 时弹出 snapshots[0]）
    while (snapshots.Count >= 2 && snapshots[1].ServerTick <= renderTick)
        snapshots.RemoveAt(0);

    // 3. 只有一个快照：直接应用
    if (snapshots.Count == 1) { ApplySnapshot(snapshots[0]); return; }

    // 4. 两个快照之间插值
    CharacterSnapshotMessage from = snapshots[0];
    CharacterSnapshotMessage to = snapshots[1];
    float alpha = (float)((renderTick - from.ServerTick) / (to.ServerTick - from.ServerTick));
    Vector3 position = Vector3.Lerp(from.Position, to.Position, alpha);
    Quaternion rotation = Quaternion.Slerp(from.Rotation, to.Rotation, alpha);
    Vector3 velocity = Vector3.Lerp(from.Velocity, to.Velocity, alpha);
    movement.ApplyNetworkState(position, rotation, velocity, to.MovementMode);
}
```

**插值延迟（Interpolation Delay）的作用**：
- 网络有抖动，快照可能延迟到达。
- 维护一个 6 Tick（约 100ms @60Hz）的延迟缓冲区，确保始终有两个快照可插值。
- 代价是模拟代理比权威位置延迟约 100ms，但视觉上完全平滑。

### 7.3 `GameNetDriver.cs`

**作用**：**整个网络系统的中枢**，管理传输层、连接集合、握手状态机、消息分发、Tick 循环、对象生成/销毁、状态复制。对应 UE 的 `UNetDriver`。

#### 常量

```csharp
public const ushort DefaultPort = 7777;
public const ushort DefaultTickRate = 60;                    // 60 Hz
public const ushort DefaultStateReplicationRate = 5;         // 状态复制频率（每 12 Tick 一次）
public const ushort DefaultMovementSnapshotRate = 20;        // 移动快照频率（每 3 Tick 一次）
public const float HandshakeTimeoutSeconds = 10f;
```

**为什么状态复制频率低于移动快照频率**：
- 状态（如血量）变化少、重要性高 → 低频 Reliable（每 12 Tick ≈ 5Hz）。
- 移动快照变化快、可容忍丢包 → 高频 Unreliable（每 3 Tick ≈ 20Hz）。

#### 启动方法

```csharp
public void StartDedicatedServer(ushort port)
public void StartClient(string address, ushort port, string displayName)
```

- `StartDedicatedServer`：传输层监听，设 Mode。
- `StartClient`：传输层连接，创建 `ServerConnection`，设 Mode。

#### `Tick(float unscaledDeltaTime)` — 核心循环

```csharp
public void Tick(float unscaledDeltaTime)
{
    if (!IsRunning) return;

    transportEvents.Clear();
    transport.PollEvents(transportEvents);           // 1. 拉取传输事件
    for (int i = 0; i < transportEvents.Count; i++)
        ProcessTransportEvent(transportEvents[i]);   // 2. 逐个处理

    TickHandshakeTimeouts(safeDeltaTime);            // 3. 握手超时检测
    AdvanceServerClock(safeDeltaTime);               // 4. 推进服务端时钟
    ReplicateActorStates();                          // 5. 复制组件状态（服务端）
    ReplicateCharacterSnapshots();                   // 6. 复制移动快照（服务端）
    transport.Flush();                               // 7. 刷新发送缓冲
}
```

**Tick 顺序的设计理由**：
1. 先处理网络事件（新连接、数据包、断开）—— 确保状态最新。
2. 超时检测 —— 清理卡住的握手。
3. 时钟推进 —— 为后续复制提供正确的 Tick。
4. 状态复制 —— 基于最新 Tick 判断是否到了复制间隔。
5. 移动快照 —— 同上，但频率更高。
6. 最后 Flush —— 批量发送，减少系统调用。

#### 事件分发：`HandlePacket`

```csharp
private void HandlePacket(GameNetConnection connection, byte[] packet)
{
    // 按首字节尝试识别消息类型，依次尝试四种协议：
    if (ConnectionProtocol.TryReadMessageType(...)) { ... return; }
    if (ActorProtocol.TryReadMessageType(...))      { ... return; }
    if (ObjectReplicationProtocol.TryReadMessageType(...)) { ... return; }
    if (CharacterMovementProtocol.TryReadMessageType(...)) { ... return; }

    RejectOrClose(connection, InvalidPacket, "Unknown packet");
}
```

**为什么按顺序尝试而非直接 switch**：四种协议的消息类型空间不重叠（1-6, 16-18, 32, 48-50），但首字节值可能落在某协议的枚举范围外。按优先级依次尝试，保证正确分发。

**Ready 检查**：除 Connection 消息外，所有消息必须在连接 `Ready` 后才能处理，否则拒绝。

#### 握手状态机（服务端）：`HandleServerPacket`

```
AwaitHello  --ClientHello-->  验证版本/Schema  --ServerChallenge-->  AwaitLogin
AwaitLogin  --ClientLogin-->  验证 Nonce/Name  --ServerWelcome-->   AwaitReady
AwaitReady  --ClientReady-->  验证 ConnectionId  --> Ready
```

每一步都严格校验当前状态与消息类型的匹配，不匹配则 `RejectOrClose`。

#### 握手状态机（客户端）：`HandleClientPacket`

```
AwaitChallenge  --ServerChallenge-->  验证 Nonce  --ClientLogin-->  AwaitWelcome
AwaitWelcome    --ServerWelcome-->    保存 ConnId/Tick  --ClientReady-->  Ready
```

客户端收到 `ServerWelcome` 时会同步时钟：

```csharp
connection.ServerTickAtWelcome = serverTickAtWelcome;
connection.ServerTickRate = tickRate;
serverTick = serverTickAtWelcome;  // 全局时钟对齐
serverTickAccumulator = 0d;
```

#### 时钟推进：`AdvanceServerClock`

```csharp
private void AdvanceServerClock(float deltaTime)
{
    ushort tickRate = Mode == DedicatedServer
        ? DefaultTickRate
        : ServerConnection?.ServerTickRate ?? 0;

    double tickInterval = 1d / tickRate;
    serverTickAccumulator += deltaTime;
    uint elapsedTicks = (uint)(serverTickAccumulator / tickInterval);
    if (elapsedTicks == 0) return;

    serverTick += elapsedTicks;
    serverTickAccumulator -= elapsedTicks * tickInterval;
}
```

- 服务端用固定 60Hz。
- 客户端用服务端在 Welcome 中告知的 TickRate。
- 累积器模式确保即使帧率波动也能正确推进 Tick。

#### 客户端时钟同步：`SynchronizeClientServerTick`

```csharp
private void SynchronizeClientServerTick(uint receivedServerTick)
{
    if (Mode == Client && (serverTick == 0 || unchecked(receivedServerTick - serverTick) < 0x80000000u))
    {
        serverTick = Math.Max(serverTick, receivedServerTick);
    }
}
```

- 客户端每次收到服务端 Tick 时，如果服务端 Tick 比本地新（环形比较），就更新本地。
- **只增不减**：防止网络延迟导致的旧包让时钟倒退。

#### Spawn 流程：`SpawnServerObject` / `RegisterServerObject`

```csharp

public NetworkIdentity RegisterServerObject(NetworkIdentity identity, ...)

    for (int i = 0; i < targets.Count; i++)
        OpenActorChannel(targets[i], registered);  // 向所有 Ready 连接开 Channel
    NetworkObjectSpawned?.Invoke(registered);
    return registered;
}
```

#### `OpenActorChannel`

```csharp
private bool OpenActorChannel(GameNetConnection connection, NetworkIdentity identity)
{
    if (connection.TryGetActorChannelByNetId(identity.NetId, out _)) return true; // 已存在

    ActorReplicationChannel channel = connection.FindOrCreateLocalActorChannel(identity);
    byte[] packet = ActorProtocol.CreateActorChannelOpen(
        channel.ChannelId, identity.NetId, identity.PrefabId,
        identity.OwnerConnectionId, identity.AuthorityEpoch,
        identity.transform.position, identity.transform.rotation);
    TrySendReliable(connection, packet, "ActorChannelOpen");
    return true;
}
```

#### 初始状态发送：`SendInitialObjectStates`

收到客户端 `ActorChannelOpenAck` 后，服务端立即发送所有组件的初始状态（`force: true`），走 Reliable。

#### 状态复制循环：`ReplicateActorStates`

```csharp
private void ReplicateActorStates()
{
    uint replicationInterval = DefaultTickRate / DefaultStateReplicationRate; // 60/5=12 Tick
    foreach (connection in readyConnections)
        foreach (channel in connection.ActorChannels)
            if (channel.SpawnAcked && serverTick - channel.LastReplicatedTick >= interval)
            {
                channel.LastReplicatedTick = serverTick;
                foreach (replicator in channel.ObjectReplicators)
                    if (replicator.TryCaptureState(force: false, out seq, out state))
                        SendUnreliable(connection, ObjectReplicationProtocol.CreateObjectState(...));
            }
}
```

- 按连接 × Channel × 组件三层遍历。
- `TryCaptureState(force: false)` 做增量检测，状态没变就跳过。
- 走 **Unreliable**：状态更新频率高，丢一两个无所谓，用 Reliable 会堆积。

#### 移动快照循环：`ReplicateCharacterSnapshots`

与状态复制类似，但：
- 频率更高（每 3 Tick）。
- **跳过拥有者连接**（`channel.Actor.OwnerConnectionId == connection.ConnectionId`）：拥有者通过 MoveAck 获取位置，不需要 Snapshot。
- 只发有 `CharacterNetworkMovement` 组件的对象。

#### 断线清理：`CleanupNetworkStateForConnection`

- 客户端：清空所有网络对象。
- 服务端：Despawn 该连接拥有的所有对象（触发 ActorChannelClose 通知其他客户端）。

## 12. 关键工作流详解

### 12.1 连接握手完整流程

```
Client                                         Dedicated Server
  |                                                |
  |--- UTP Connect (传输层) ----------------------->|
  |                                          AwaitHello
  |--- ClientHello (ProtocolVer, Schema, Nonce) -->|
  |                                     校验版本+Schema, 生成 ServerNonce
  |                                          AwaitLogin
  |<-- ServerChallenge (回显ClientNonce, ServerNonce)|
  |                                          AwaitWelcome
  |--- ClientLogin (ServerNonce, DisplayName) ----->|
  |                                     校验Nonce, 分配ConnectionId
  |                                          AwaitReady
  |<-- ServerWelcome (ConnectionId, Tick, Rate) ----|
  |--- ClientReady (ConnectionId) ----------------->|
  |     双方进入 Ready                              Ready
  |                                                |
  |     → ServerGameMode.HandleConnectionReady     |
  |       创建 ServerPlayerController              |
  |       Spawn Pawn (ActorChannelOpen → ...)      |
```

### 12.2 网络对象 Spawn 完整流程

```
Server                          Client A (Owner)         Client B (Observer)
  |                                |                        |
  | SpawnServerObject(prefabId)    |                        |
  | → Registry 分配 NetId          |                        |
  | → Role = Authority             |                        |
  |                                |                        |
  |--- ActorChannelOpen(NetId, Owner=A, ...) -->|          |
  |--- ActorChannelOpen(NetId, Owner=A, ...) -------------->|
  |                           PrefabRegistry.TryInstantiate  |
  |                           Role = AutonomousProxy         |
  |                           Role = SimulatedProxy          |
  |                           Registry.Register              |
  |<-- ActorChannelOpenAck(ChannelId, NetId) ---|           |
  |<-- ActorChannelOpenAck(ChannelId, NetId) -----------------|
  | channel.SpawnAcked = true      |                        |
  |                                |                        |
  |--- InitialObjectState(Reliable) --------->|             |
  |--- InitialObjectState(Reliable) ------------------------>|
  |                           Replicator.TryApplyState       |
  |                           Replicator.TryApplyState       |
```

### 12.3 属性复制流程（以血量为例）

```
Server (Authority):
  ReplicatedHealth.SetHealth(150)
  ↓ Tick → ReplicateActorStates (每 12 Tick)
  ↓ ObjectReplicator.TryCaptureState
    → CaptureReplicatedState() → writer.WriteInt32(150) → byte[4]
    → 与 lastSentState 比较（增量检测）
    → 分配 Sequence
  ↓ ObjectReplicationProtocol.CreateObjectState → Unreliable Send

Client (SimulatedProxy):
  HandleObjectReplicationPacket
  → TryReadObjectState → ObjectStateMessage
  → channel.TryGetObjectReplicator(ReplicationId)
  → replicator.TryApplyState(Sequence, State, isInitial)
    → IsNewerSequence 检查
    → Target.TryApplyReplicatedState
      → ReplicationStateReader.TryReadInt32 → health = 150
      → OnReplicatedStateApplied (日志)
```

### 12.4 移动预测与纠错流程（AutonomousProxy）

```
Client (AutonomousProxy):                     Server (Authority):
  LateUpdate                                    HandleServerCharacterMove
  ↓ CaptureAndSendLocalMove                     ↓ TryProcessServerMove
  ↓ 记录 SavedMove(预测位置)                      校验 DeltaTime、输入模长
  ↓ SendCharacterMove(Unreliable)        <---   检查序列号是否更新
  ↓                                             SetControlRotation(yaw)
  ↓                                             movement.SimulateNetworkMove(input, dt)
  ↓                                             lastServerMoveSequence = seq
  ↓                                             CreateServerAck(serverTick)
  ↓                                     --->    SendUnreliable(ServerMoveAck)
  ReceiveServerMoveAck                          
  ↓ 对比预测位置 vs 权威位置                       
  ↓ 误差 ≤ 5cm → 丢弃已确认移动，不纠错             
  ↓ 误差 > 5cm:                                  
    ApplyNetworkState(权威位置)                   
    重放所有未确认的 SavedMove                     
    更新各 SavedMove 的预测位置                    
    correctionCount++                           
```

### 12.5 模拟代理插值流程（SimulatedProxy）

```
Server (每 3 Tick):
  ReplicateCharacterSnapshots
  ↓ 跳过拥有者连接
  ↓ CreateServerSnapshot(serverTick, position, ...)
  ↓ SendUnreliable(TransformSnapshot)

Client (SimulatedProxy):
  ReceiveSnapshot
  ↓ 添加到 snapshots 缓冲区（最多 32 个）

  InterpolateSimulatedProxy (每帧 LateUpdate)
  ↓ renderTick = serverTick - 6  (延迟 ~100ms)
  ↓ 丢弃 snapshots[1].ServerTick ≤ renderTick 的旧快照
  ↓ 在 snapshots[0] 和 snapshots[1] 之间插值
  ↓ alpha = (renderTick - from.Tick) / (to.Tick - from.Tick)
  ↓ Vector3.Lerp(position) + Quaternion.Slerp(rotation)
  ↓ movement.ApplyNetworkState(插值结果)
```

### 13.3 关键设计原则总结

1. **权威服务器模型**：所有状态以服务端为准，客户端只能预测。
2. **严格的状态机**：握手每一步都校验状态，防止协议注入。
3. **增量复制**：状态没变就不发，节省带宽。
4. **序列号防回绕**：用环形比较（差值 < 半圈）处理 uint/ushort 回绕。
5. **AuthorityEpoch 防幽灵包**：对象重建后旧包自动失效。
6. **可靠/不可靠分流**：关键消息 Reliable，高频消息 Unreliable。
7. **分层解耦**：Transport 可替换，Protocol 纯序列化，Driver 纯调度，GameMode 纯逻辑。
8. **组件级复制**：每个 NetworkBehaviour 独立序列化，只复制变化的部分。
9. **插值延迟缓冲**：模拟代理延迟 ~100ms 显示，换取视觉平滑。
10. **预测纠错阈值**：5cm 以下不纠错，避免抖动。
